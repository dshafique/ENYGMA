0.1  |  What ENYGMA is

Part 0 · Foreword0.1

ENYGMA turns a recording of a meeting into something you can act on: an attributed transcript, a summary where every claim points back at the moment it was said, and a list of what anybody committed to do.

The problem it solves

An intern sits in meetings where decisions are made quickly, by people who already share years of context, using words nobody stops to define. Two hours later he has three pages of notes, no idea which parts mattered, and a handful of terms he did not want to interrupt to ask about.

Recording the meeting does not fix this. A ninety-minute audio file is worse than notes: it contains everything and surfaces nothing. What is needed is the same recording, indexed by speaker and by moment, with the decisions pulled out and every one of them still attached to the audio that proves it.

What makes it different from a transcription service

Three things, all of which follow from who it is for.

It runs on hardware its operator owns. There is no account, no dashboard belonging to somebody else, and no company that can change its terms, raise its price, or read the recordings. The only third party that ever sees the audio is the transcription model, and that relationship is one API key that the operator holds and can revoke.

Every claim is checkable. A summary that asserts a decision without pointing at the moment it was made is an assertion the operator cannot verify. Every decision, open question and action in ENYGMA carries a timestamp that seeks the audio. If a claim cannot point at a moment, it is left out.

It teaches. Hold any word in a transcript and ENYGMA explains it; ask for more and the term opens a conversation. The system is built on the assumption that its operator is learning, and that the words he did not want to interrupt to ask about are the highest-value thing in the recording.

What it is not

  • Not multi-tenant, and deliberately not built so that it could become multi-tenant later. One operator, one database, one unix user. Every place where a second user would need to be accommodated is a place where a simpler decision was made instead.
  • Not a note-taking app. It does not compete with the operator's own notes; it indexes the recording those notes were taken from.
  • Not a system of record for anyone else. Nothing synchronises outward. A meeting can be copied out as Markdown on demand, which is a one-directional escape hatch, not an integration.
  • Not a source of truth about people. Speaker names are assigned by the operator, by hand, and the model never guesses one. Two similar names are two people until the operator says otherwise.
Note ENYGMA shares a machine with PHNTM and shares nothing else: not a database, not a session secret, not an API key, not a unix user. The isolation is enforced by file permissions, and Chapter 4 shows the proof rather than asserting it.

0.2  |  The Five Tenets

Part 0 · Foreword0.2

Five commitments. Every design decision in this system can be traced to one of them, and where two of them conflict the earlier one wins.

Tenet 01

No password exists in this product

Authentication is a passkey: a private key held by the device's secure hardware, released by a fingerprint. There is nothing to phish, nothing to reuse from another site, and nothing a database breach could reveal, because the server stores only public keys.

A PIN and recovery codes exist as the way back in when the passkey is unavailable. They are hashed with Argon2id, never a fast hash, and they sit behind a single lockout counter shared by every method — five failures across passkey and PIN combined, not five each.

Tenet 02

Isolation is filesystem permissions, not discipline

ENYGMA runs as its own unix user, with its own home directory at mode 750 and its data and audio directories at 700. The isolation from PHNTM is not a convention that a future change might forget; it is a property the kernel enforces on every read.

The session cookie is named with the __Host- prefix, which forbids a Domain attribute. The cookie therefore cannot be scoped to arkhm.io — not by policy, but by construction.

Tenet 03

Migrations are forever-additive

Never drop a column, never rename one. To remove a column, stop writing to it. A migration that only ever adds is a migration that can be applied to any older database, which means a backup from any point in the system's life can still be restored and brought forward.

Tenet 04

Every claim carries the moment it came from

A summary is a set of assertions about what happened. An assertion the operator cannot check is worse than no assertion, because it is trusted.

Every decision, open question and action in ENYGMA is stored with the millisecond offset it came from, rendered as a timestamp the operator can click to hear it. The prompt sent to the model says explicitly: if you cannot point at a moment, leave the item out. This survives the copy-out too — a meeting exported as Markdown carries its timestamps with it, because pasting a summary somewhere else is exactly where an unsourced claim does damage.

Tenet 05

Empty beats invented

Where the system has no real answer it says so and shows nothing. Home has a panel for headlines in the operator's field; no feed is connected, so it says that plainly rather than displaying something plausible. Chat, with no model reachable, returns what the glossary actually knows and states that it cannot go further. The transcription prompt is told to write [inaudible] rather than invent words.

A blank panel is a small failure. A confidently wrong one is a large failure that looks like a success, and the operator has no way to tell them apart.

0.3  |  How to read this manual

Part 0 · Foreword0.3

The two reading orders

Reader A, the operator

You want to use the system that is already running. Read Chapter 1 for what the five tabs are, Chapter 15 for daily use, and Chapter 12 for how to get it onto a second device. Keep Chapter 17 nearby: it is the list of things that can go wrong and what each one means. Everything else can wait until it breaks.

Reader B, the builder

You are rebuilding this from a clean machine, or you are the person who inherits it. Read straight through. Parts 2 and 3 are the build; Part 4 is the half that is easy to get subtly wrong and hard to debug afterwards. Appendix D — the scar list — will save you the most time of anything here.

What you need to know going in

  • A shell, ssh, and enough comfort with a Linux host to read journalctl output without panic.
  • Nothing about Python. You will run scripts, not write them.
  • Nothing about the browser. The interface explains itself.

If something here is wrong

The source tree is canonical. If a command in this manual fails and the source disagrees with the manual, the source is right and this document is stale — re-issue it at the next edition rather than working around it. The manual's edition is the commit it was written against, so the disagreement can always be located precisely.

Scar An earlier deployment of this system re-installed a stale copy of itself and reported complete success: correct output, all tests passing, healthy service. It was three days behind. Every version number in this manual, and the mark in the corner of every screen, exists because of that afternoon.

Chapter 1  |  The product surface

Part 1 · Concept01

Five destinations, one shell. A nav rail on a desktop, a tab bar on a handset, and the same five places either way.

TabAnswersHolds
HomeWhat should I look at now? Recent meetings, open actions, headlines, what ENYGMA has learned, counts. Every panel is a door into another tab.
MeetingsWhat happened in this one? The list and the reader: search, status filters, day groups; then speakers, summary, transcript, actions and the audio.
ChatWhat does this mean? Threads. A thread can start empty or from a word held down in a transcript, in which case the term arrives as the first question.
Action itemsWhat do I owe anybody? Every commitment across every meeting, open and done, each linking back to the moment it was said.
DirectoryWho is this person? Everyone who has spoken, and the meetings they appeared in. A person exists because a speaker label was given a name.

Settings is not a tab. It sits at the foot of the rail on a desktop and in the header row on a handset, because it is a place you visit rarely and deliberately.

What it accepts

Audio, dropped onto the Meetings tab: mp3, wav, m4a, aac, ogg, flac, aiff. Up to 500 MB each by default. Files are content addressed by SHA-256, so the same recording dropped twice is one meeting whatever it was called the second time. That is the only deduplication rule: exact, never fuzzy, never guessing that two files are "probably" the same.

What it produces

1. The attributed transcript

Every segment carries a speaker label, a start and an end. Labels begin as SPEAKER 1, SPEAKER 2 and are given real names by the operator, by hand. The model is instructed never to guess a name even if one is said aloud, because a name in a transcript is evidence and a guessed name is a fabrication that looks like evidence.

2. The checkable summary

An abstract of two or three sentences, then decisions, open questions and actions — each one carrying the timestamp it came from. Clicking a timestamp seeks the audio to that moment.

3. The glossary and the conversation

Holding a word in the transcript raises a small panel with a definition and a Learn more that opens a Chat thread named for that term, with the question already asked and answered. The glossary ships with the vocabulary of the operator's field and grows by use.

4. A copy, on demand

Copy as Markdown puts the whole meeting on the clipboard: title, date, who was present, abstract, decisions and questions with their timestamps, actions as checkboxes with owners resolved to real names, and a closing line stating which model produced it and that speaker names are not model-verified. One direction, on demand, nothing stored.

Process model

One process. Uvicorn serves the HTTP surface on the main thread; a single background thread runs the transcription worker, one recording at a time. There is no queue broker, no second service and no scheduler, because one operator dropping a few files a week does not have a queueing problem, and machinery that is not there cannot fail at three in the morning.

Why FastAPI

Server-rendered Jinja templates, no front-end framework, no build step. The entire client is one CSS file and one JavaScript module, both served directly. A deploy is copying files and restarting a service. There is no node_modules anywhere in the runtime path, which means there is no supply chain in the runtime path either.

Why SQLite

One operator, one machine, single-digit gigabytes. SQLite in WAL mode handles this with room to spare, and it makes the backup story trivial: the entire system's memory is one file that can be copied, verified and restored in seconds. A database server would add a second thing to secure, a second thing to back up, and a second thing to be running before the app can start.

Note WAL mode is why backups are taken through SQLite's own backup API rather than cp. A file copy taken mid-write is a torn database that looks fine until the day you need it. See Chapter 16.

Chapter 3  |  Data flow, end to end

Part 1 · Concept03

Nine stages from a dropped file to a summary on screen. Every stage either advances the recording's status or fails it with a sentence.

The pipeline

  1. Drop. The browser posts the file to /upload. A stale session is refused here with reason: stale, which raises the re-auth sheet rather than failing silently.
  2. Validate before writing a byte. Extension must be a known audio type; size must be under the ceiling. Rejection is a sentence saying which rule was broken.
  3. Stream and hash together. The file is written to a temporary name while SHA-256 is computed over the same pass, so a 400 MB file is read once, not twice.
  4. Deduplicate. If that hash already exists, the temporary file is discarded and the existing recording is returned, marked as a duplicate. Nothing is overwritten.
  5. Commit. The file is renamed to uploads/<first-16-of-hash>.<ext> and a row is inserted with status queued. The path is stored POSIX-style regardless of the client's platform.
  6. Claim. The worker takes one queued recording inside a BEGIN IMMEDIATE transaction and marks it transcribing, so two claims can never race.
  7. Transcribe. Under 20 MB the audio goes inline as base64; above that it is uploaded via the Files API and referenced by URI. The model returns JSON segments with speaker, start, end and text.
  8. Summarise. The transcript is rendered to timestamped text and sent back for an abstract, decisions, questions and actions — each with the moment it came from.
  9. Write results atomically. Segments, speakers, summary and actions are written in one transaction, and the recording flips to ready. Completed actions are preserved across a re-run; only open ones are replaced.

Status states, complete list

StateMeansWhat moves it on
queued Stored on disk, waiting for the worker. The worker, within the poll interval — three seconds by default.
transcribing Claimed. The model is working. Success, or an exception that fails it with a reason.
ready Transcript, summary and actions are written. Nothing. This is the resting state.
failed Something threw. The reason is stored and shown verbatim. Try again on the meeting, which requeues it without re-uploading.
Scar A recording is marked transcribing before the work starts. If the process dies in that gap — a restart, the memory ceiling, a power cut — nothing would ever pick it up again, because the worker only claims queued. The operator would watch a progress bar that could never finish. requeue_stuck() runs at startup and puts them back, with a note saying so.

The stub backend

With ENYGMA_PIPELINE=stub the entire application runs with no API key and no network, producing deterministic placeholder transcripts. This is not a toy: it is how the interface was built before the bill started, it is what the test suite runs against so the tests never depend on a third party being up, and it is the safe default in a fresh .env.

The interface never lets the stub be mistaken for the real thing. An amber banner sits above the dropzone, and Settings reports the pipeline as STUB.

Why a memory ceiling

The machine is shared. A leak or a runaway on ENYGMA's side must not be able to pressure PHNTM out of memory. MemoryMax=8G means the kernel kills ENYGMA rather than letting it take the machine down with it, and Restart=on-failure brings it back. The interrupted-recording recovery in Chapter 3 exists precisely so that this is survivable.

Isolation, proved rather than asserted

The installer sets the home directory to 750 and the data and upload directories to 700, then verifies it by attempting the read as another account. The relevant part of the install output: 

$ sudo bash deploy/install-on-spark.sh
==> checks
    healthz: {"ok":true,"app":"enygma","port":4073,"version":"7.2026.08.27.0553"}
    no other account can read the database, the audio or the secret
Scar adduser creates home directories world-readable on most distributions. The first version of the installer used it and stopped there, which meant the arkhm account could read every one of Yahya's recordings and his database. This was found by running the installer as root in a scratch container and actually trying the read. The chmod lines and the proof loop both date from that.

Disk

Audio costs roughly 75 MB per hour of meeting. The alarm is set at 200 GB, which is about 2,600 hours. Quotas were preferred but are not enabled on this filesystem, so an hourly alarm is installed instead — /etc/cron.hourly/enygma-disk, reporting to journalctl -t enygma-disk.

Warning An alarm reports; it does not stop the write. SQLite behaves badly on a full disk, and the disk is shared with PHNTM. If the alarm fires, act on it.

The application ran, the tests passed, and ENYGMA_PIPELINE=gemini had never once been capable of working — the first real meeting failed on ImportError. There is now a test asserting the dependency is declared, and the backend's import error names the command to fix it instead of saying cannot import name 'genai'.

Front-end stack

There isn't one. Two CSS files and one JavaScript module, served directly, no bundler.

  • tokens.css is generated by tools/gen_tokens.py from a single palette. Raw hex anywhere else fails review.
  • app.css contains references only — every colour is a var().
  • app.js is one ES module. Every block guards on its own elements, so a page without a dropzone simply skips that block.
Scar An undefined CSS custom property does not warn. The whole declaration becomes invalid, the browser drops it, and a layout quietly collapses with nothing in the console. tools/check_tokens.py fails the build on any var() that nothing defines, and the installer runs it. It has caught this class of bug more than once.

Fonts and the mark

Inter for prose, JetBrains Mono for labels, timestamps and anything that is a literal. The mark is a 4×4 cipher grid on a 64-unit box — cell 13, gap 3, offset 1.5, radius 1.6, with four cells voided — and it is drawn from those numbers everywhere it appears, including the PWA launcher icons, which are generated by tools/gen_icons.py rather than traced. The icon and the mark cannot drift apart because they are the same specification.

Chapter 6  |  Accounts, network topology and cost

Part 2 · Bill of Materials06

Required accounts

Cloudflare — free

Holds the arkhm.io zone and terminates the tunnel. Already in use for PHNTM; ENYGMA adds one hostname and one DNS record to the existing account and tunnel.

Google Cloud / AI Studio — paid tier, required

Supplies the Gemini API key. The paid tier is not optional here, and not for rate limits. On the free tier Google's terms permit prompts and responses to be used to improve their products. What ENYGMA sends is other people's voices, client names and contract terms from an employer's meetings. That cannot go through a tier whose terms allow training on it.

Warning Do not run a real meeting through a project that is still on the free tier. Confirm the project reads as paid before the first upload, not after.

The key lives in its own Google Cloud project, not PHNTM's. The project is the unit of attribution and revocation: a second key inside PHNTM's project shares quota, billing lines and blast radius, and killing the project kills both systems. Restrict the key to the Gemini API.

A domain

arkhm.io, already owned. ENYGMA occupies the enygma subdomain and nothing else.

Network topology

Yahya's phone / laptop
        │  https
        ▼

Chapter 7  |  Deployment

Part 3 · Build07

One script does the whole thing and is safe to run twice. It refuses to proceed rather than guessing, and it runs the test suite before it restarts anything.

Step 1 — Get the release onto the host

From a clone, which is the recommended path:

$ git clone https://github.com/dshafique/ENYGMA.git ~/enygma-release
$ cd ~/enygma-release
$ python3 tools/stamp_release.py
Mk II.7   build 7.2026.08.27.0553

stamp_release.py writes VERSION and MARK from the commit count. Both are build artifacts and are not in the repository, because committing them would mean the number changes the number it reports.

Warning If you deploy from an extracted archive instead of a clone, extract into a clean directory. Unpacking over an old copy leaves deleted files behind, and a stale template shadows a new one.

Step 2 — Run the installer

$ sudo bash deploy/install-on-spark.sh

In order, it:

  1. Announces the release it is about to install and the one it is replacing. A stale deployment is visible before anything is touched.
  2. Checks Python is 3.10 or newer, and that venv is available.
  3. Checks the port. If something answers on 4073 and it is not ENYGMA, it stops. Two applications on one port is exactly the coupling this design avoids.
  4. Creates the unix user if absent, and sets the permissions that make isolation real.
  5. Replaces release-owned directories — src/ tools/ tests/ deploy/ — outright, then unpacks. data/, uploads/, .env and .venv/ are the operator's and are never touched.
  6. Builds the virtualenv and installs requirements.txt.
  7. Writes .env if absent, with a freshly generated session secret at mode 600. An existing one is left alone.
  8. Proves it before wiring it up: runs migrations, the token lint, the .env check and the full test suite as the enygma user. A failure here stops the deployment with the old version still running.
  9. Installs the systemd unit and restarts.
  10. Verifies /healthz answers and that no other account can read the database, the audio or the secret.

Step 3 — Backups, once per machine

$ sudo bash deploy/install-backups.sh

Takes one immediately so the first backup is not scheduled for tonight, verifies it by restoring it, installs /etc/cron.daily/enygma-backup, then runs the scheduled job directly to prove the schedule itself works and not merely the command.

What a correct install looks like

==> release 7.2026.08.27.0553  (from /home/arkhm/enygma-release)
    replacing build 6.2026.08.27.0546
    python3 3.12
==> code into /home/enygma/app
==> migrations and tests, as enygma
    applied 007_… (none pending)

Chapter 8  |  Configuration

Part 3 · Build08

Everything comes from the environment. Nothing is hardcoded, and .env is data — it is parsed, never executed.

Editing it safely

$ sudo -u enygma nano /home/enygma/app/.env
Warning Paste that line on its own. An editor takes over the terminal, so anything pasted after it goes into the file instead of the shell.

Checking it before restarting

$ sudo -u enygma bash -c "cd /home/enygma/app && .venv/bin/python tools/check_env.py"

Chapter 10  |  Cloudflare Tunnel and DNS

Part 4 · Access & Auth10

Mental model

cloudflared runs on the host and makes an outbound connection to Cloudflare's edge. Requests for enygma.arkhm.io arrive at the edge and are routed back down that connection. The host opens no port; there is nothing to forward and nothing exposed.

One cloudflared instance serves both applications. Its config maps hostnames to local ports, and ENYGMA's rule must sit above the catch-all, because the first match wins.

The two pieces

1. An ingress rule in the cloudflared config:

ingress:
  - hostname: enygma.arkhm.io
    service: http://127.0.0.1:4073
  - hostname: arkhm.io
    service: http://127.0.0.1:4063
  - service: http_status:404          # catch-all, always last

2. A DNS record in the zone:

TypeNameTargetProxy
CNAMEenygma<tunnel-uuid>.cfargotunnel.comProxied
Warning The orange cloud is not optional. An unproxied CNAME to cfargotunnel.com does not resolve at all — the name only exists inside Cloudflare's network. A grey cloud here produces Server Not Found, which reads like a DNS outage.

deploy/dns-record.sh reads the tunnel config and prints exactly the record required. It is read-only and changes nothing.

Warning The cloudflared config is serving PHNTM right now. Back it up before editing, validate after, and restore on any doubt. deploy/add-tunnel-route.sh does all three.
Scar cloudflared tunnel ingress validate --config X puts the flag in the wrong place; the flag must precede the subcommand. Worse, cloudflared exits 0 on that usage error, so a script that trusted the exit code printed ingress rules are valid having validated nothing at all. The script now reads the command's output, and restores the backup if it cannot find an explicit success.

Verifying, from outside

$ curl -s https://enygma.arkhm.io/healthz
{"ok":true,...,"mark":"Mk II.7"}
$ curl -s -o /dev/null -w "%{http_code}\n" https://arkhm.io/
200

Always check PHNTM in the same breath. The whole risk of touching this config is that ENYGMA comes up and something else quietly goes down.

Chapter 11  |  Passkeys and the freshness window

Part 4 · Access & Auth11

Mental model

A passkey is a private key generated by the device and held in its secure hardware, released only by a biometric or device unlock. The server stores the matching public key and a signature counter, and nothing else. There is no shared secret to steal.

The credential is bound to the origin that created it — enygma.arkhm.io, exactly. This is why ENYGMA_RP_ID and ENYGMA_ORIGIN must match what the browser sees, and why a passkey made against one hostname will not work against another.

Two levels of authorisation

Reading and writing are different questions, and ENYGMA answers them differently.

LevelNeedsCovers
ViewA valid session, any age Every page, the audio, the Markdown copy, term lookups. Anything the page is already showing.
WriteA session verified within the freshness window Uploads, ticking actions, naming speakers, sending chat, minting a setup code, changing the PIN.

The window is ENYGMA_REAUTH_MINUTES, default 30. Going stale does not eject you: you keep reading, and the first write raises a small sheet asking you to confirm. Prove it is you and the original action is retried automatically — the page, the scroll position and anything typed all survive.

Scar Before that sheet existed the window was five minutes, and a stale upload returned 401 which the interface parsed as an empty result list and rendered as nothing at all. The file appeared to vanish. A silent no is the worst possible answer to did that work; every write now goes through one wrapper that either succeeds, re-authenticates and retries, or says what went wrong.

Lockout

Five failures across passkey, PIN and setup code combined — not five each — then a delay that doubles each further round, capped at an hour.

FailuresDelay
530 seconds
1060 seconds
204 minutes
50+1 hour, capped

A flat delay is the wrong shape for a short PIN. A fat finger still costs thirty seconds; an exhaustive search of a four-digit PIN now costs more than a month of continuous attempts. A successful authentication clears the counter entirely.

The lockout is server-side and keyed on the account. A client-side countdown is decoration.

Chapter 12  |  Setup codes, PIN and adding a device

Part 4 · Access & Auth12

A passkey belongs to the device that made it. A second device has no way in on its own, and the two ways to give it one are not interchangeable.

The two credentials, which are not the same thing

PINSetup code
Looks like0125 — 4 to 10 digitsB84C-5L28 — 8 letters and numbers
LifetimeStanding, until changed10 minutes, single use
Set fromSettings → PINSettings → Set up another device

Note Typing the PIN into the setup-code field is the single most likely mistake here, and the screen now names it as such rather than saying not valid or has expired — which was true, and useless, for every possible error.

Adding a device, the recommended way

  1. On a device already signed in: Settings → Set up another device. An eight-character code appears. It is shown once and only its hash is stored.
  2. On the new device: open enygma.arkhm.io → Set up this device → enter the code.
  3. It signs that device in and immediately prompts to create a passkey there. Done.

Minting a code needs a fresh session, because it is the one credential that creates other credentials and a left-open tab should not be able to produce one. Creating a new code cancels any outstanding one: two live codes means one of them is forgotten, and a forgotten credential is the one that gets used against you.

Adding a device with the PIN instead

Open the site on the new device, choose Use PIN instead, then Settings → Add this device. This works and is the fallback when no signed-in device is to hand — but it means the standing secret gets typed on one more device, which is precisely what setup codes exist to avoid.

Removing a device

Settings → Devices → Revoke. The credential is marked revoked rather than deleted, so the record of what existed survives. A revoked passkey stops working immediately.

Chapter 13  |  Recovery procedures and threat model

Part 4 · Access & Auth13

Action: a device is lost or stolen

From any signed-in device: Settings → Devices → Revoke. Immediate.

If no other device is enrolled, sign in with the PIN first, then revoke, then enrol the replacement. If the PIN is also unknown, use the shell procedure below.

Action: locked out entirely

Shell access to the host is the ultimate authority. Nothing in the web interface can prevent an operator with root from getting back in. 

$ sudo -u enygma bash -c "cd /home/enygma/app && .venv/bin/python -c \
  \"import sys; sys.path.insert(0,'.'); from src.auth import secrets_store as s; s.set_pin('482913')\""

Then sign in with that PIN and re-enrol. Change it afterwards from Settings — a PIN that has been typed into a shell has been written to history.

Action: rotate the session signing secret

Signs every session out, everywhere, immediately. Passkeys and the PIN are unaffected; only the cookies are invalidated. 

$ sudo -u enygma nano /home/enygma/app/.env     # replace ENYGMA_SESSION_SECRET
$ sudo systemctl restart enygma

Generate one with python3 -c "import secrets; print(secrets.token_urlsafe(48))".

Action: full auth reset

Warning This removes every passkey, the PIN and every outstanding setup code. The next visitor to the site becomes the owner. Do it only with the site unreachable, or immediately before enrolling. 
$ sudo systemctl stop enygma
$ sudo -u enygma sqlite3 /home/enygma/app/data/enygma.db \
  "DELETE FROM credentials; DELETE FROM pin; DELETE FROM pairing_codes; DELETE FROM auth_attempts;"
$ sudo systemctl start enygma

Action: move to a new machine

  1. Take a backup on the old host and copy it off.
  2. Install on the new host, then stop the service.
  3. Restore the database over the fresh one (Chapter 16).
  4. Carry the .env across, or accept that a new session secret signs everyone out once.
  5. Repoint the tunnel and DNS so the origin is unchanged.
Warning Passkeys are bound to the origin, not the machine. Keep enygma.arkhm.io and every enrolled device still works. Change the hostname and every passkey is dead — plan the PIN before, not after.

What the service worker does, and does not

It caches exactly one class of thing: requests to /static/ carrying a ?v= build stamp, whose contents can never change. That is what makes the app open instantly.

It never caches a page, an API response, audio, or anything under /auth. Everything ENYGMA renders is private; a cached page is a transcript sitting on the device's disk outside the file permissions that are the entire isolation story, and still servable after a sign-out. Offline, the app does not work — which is correct, because the data lives on a machine at home and pretending otherwise would mean keeping a copy that should not exist.

Updating after a deployment

Nothing to do. Every asset URL carries the build, so a new release is a new set of URLs and the old cache is discarded on activation. Closing and reopening the app is enough; there is no cache to clear by hand.

Scar Before assets were addressed by build, a browser served a stylesheet cached days earlier against new markup. The old file had no rule for the icons, and an inline SVG with no width fills its container — so a 20-pixel icon rendered as a 750-pixel chevron across the page. Icons now carry their own width and height as attributes, so CSS is an enhancement rather than load-bearing.

Chapter 15  |  Daily use

Part 5 · Operating15

After a meeting

  1. Open ENYGMA, go to Meetings, drop the audio file on the dropzone. Several at once is fine.
  2. If you have been idle a while a sheet asks you to confirm it is you. Do so; the upload continues by itself.
  3. Watch it move queued → transcribing → ready. The page refreshes itself while something on view is running.
  4. Open it. Put real names on the speaker chips — this is the one thing the system cannot do for you, and it is what makes the Directory and the action owners meaningful.

Reading a meeting

Summary is the abstract, the decisions and the open questions. Every timestamp is a button: it seeks the audio to that moment, so any claim can be checked against what was actually said in about two seconds.

Transcript is the full record, with the current segment highlighted as the audio plays. Actions is what was committed to; ticking one here ticks it everywhere.

Looking a word up

Press and hold any word in the transcript for about half a second. A small panel gives the definition. Learn more opens a Chat thread named for that term with the question already asked, and the conversation carries on from there.

This is the feature the system was built around. The words nobody stops to define in a meeting are the highest-value thing in the recording for someone still learning the domain.

Getting something out

Copy as Markdown on any meeting puts the whole thing on the clipboard, timestamps intact, ready to paste anywhere. There is deliberately no synchronisation to another system: two homes for one summary means neither is trusted, and the half that makes ENYGMA worth having — the claim welded to the moment, with the audio a click away — is the half that a pasted page throws out.

Weekly, thirty seconds

  • Actions — anything still open that should not be.
  • Directory — any speaker still unnamed. The count is in the subtitle.
  • journalctl -t enygma-backup -n 5 — backups still running.

Chapter 16  |  Backups and restore

Part 5 · Operating16

The database is the only thing here that cannot be reproduced. Audio can be uploaded again; a transcript, a summary, a corrected speaker name and an enrolled passkey cannot.

What is backed up, and what is not

ItemBacked upWhy
data/enygma.dbYes, nightlyEverything the system has ever understood.
uploads/*NoLarge, and re-uploadable from wherever it came from. Copying 500 MB files nightly onto the same disk buys very little.
.envNoTwo values, one of which should be rotated on any restore anyway.

Why not cp

The database runs in WAL mode. A file copy taken while a write is in flight is a torn database: it copies cleanly, it looks fine, and it fails on the day you need it. tools/backup.py uses SQLite's own backup API, which produces a consistent snapshot even mid-write.

Every backup is verified when taken

A backup nobody has restored is a hope, not a backup. Each one is decompressed to a temporary file, opened, PRAGMA integrity_check run, and every expected table counted — immediately, as part of taking it. 

$ sudo -u enygma sh -c "cd /home/enygma/app && .venv/bin/python tools/backup.py"
wrote enygma-20260827-045126.db.gz  (8 KB)
restored enygma-20260827-045126.db.gz
  integrity_check: ok
  recordings             5
  transcript_segments    27
  credentials            1
  the backup opens, passes integrity check and has every table.

Restoring

$ sudo systemctl stop enygma
$ sudo -u enygma sh -c "cd /home/enygma/app && \
    gunzip -c backups/enygma-20260827-045126.db.gz > data/enygma.db"
$ sudo systemctl start enygma

This procedure has been exercised, not assumed: a live database was deliberately overwritten with garbage, SQLite confirmed it unreadable, and the backup restored every recording, segment and action intact.

Warning The backups sit on the same NVMe as the database. That covers corruption, a bad migration and an accidental delete. It does not cover losing the disk. If this data matters beyond that, copy /home/enygma/app/backups somewhere else on a schedule. The system does not pretend to have solved this.

Retention

Fourteen nights by default; older ones are pruned as each new backup is taken. Pass --keep 30 to deploy/install-backups.sh to change it.

Chapter 18  |  Releases, and what is still unproven

Part 5 · Operating18

The mark

Mk II.N, where N is the commit count of the repository the build came from. It is in the top right of every screen, in Settings, and at /healthz. A manual and a running system can always be checked against each other in one glance.

VERSION also leads with N and is appended to every static asset URL, so a browser cannot serve a cached stylesheet against newer markup.

Shipping a change

$ cd ~/enygma-release && git pull
$ python3 tools/stamp_release.py
$ sudo bash deploy/install-on-spark.sh

The installer runs the token lint, the environment check and the full test suite as the application user before it restarts anything. A failure leaves the previous version running.

What is proven

  • Isolation. Verified by attempting the read as another account.
  • Restore. Verified by destroying a live database and bringing it back.
  • Re-authentication. Verified by driving a genuinely stale session in a browser.
  • The worker's failure path. Verified with a backend that throws.
  • Truncation salvage. Verified against the exact response that failed.
  • The service worker's discretion. Verified by reading the cache after loading a meeting.

What is not

Warning Speaker attribution has never been measured. Labels come from asking a model politely in a prompt, not from a diarization system. They are a claim, not a measurement. Nobody has checked them against a known-good reference. For an operator reading his own meetings this is a fixable annoyance; before a name from here is quoted to anybody else, it should be verified by ear.
  • Transcript accuracy has not been compared against a reference transcript of the same audio.
  • Long recordings — the practical duration ceiling has not been established, only that one exists.
  • Off-machine backup does not exist. Disk failure is total loss.
  • The consent conversation about recording an employer's meetings is a matter between the operator and the people in the room, and no amount of engineering settles it.
Note This chapter should shrink with each edition. A manual that claims everything works is a manual nobody has tested.

ReferenceD

Every one of these looks like an odd decision until you know what caused it. They are collected here because this is the appendix that will save the next person the most time.

What happenedWhat it now does
adduser left the home directory world-readable, so another account on the machine could read every recording and the database. The installer chmods 750 and 700, then proves it by attempting the read as another account.
A semicolon inside an English sentence in a migration comment ended the statement early; the rest of the prose became SQL and failed as near "the": syntax error. Comments are stripped before splitting on semicolons, respecting quoted strings.
CSS referenced custom properties that nothing defined. The declarations were silently dropped and a layout collapsed with nothing in the console. check_tokens.py fails the build on any unresolved var(). The installer runs it.
A route rendered a template nobody had looked at in weeks, because every test called the page beneath it directly. Every page is requested over HTTP in the suite, and a test asserts every template main.py names exists.
An install re-deployed a stale extraction and reported complete success. It was three days behind. Every build carries a mark. The installer announces what it is installing and what it is replacing; /healthz reports it.
cloudflared exited 0 on a usage error, so a script reported "ingress rules are valid" having validated nothing. The script reads the command's output, and restores its backup unless it finds explicit success.
A browser served a stylesheet cached days earlier against new markup. Icons had no width rule, and an inline SVG with no width fills its container — a 20px icon became a 750px chevron. Every asset URL carries the build. Icons also carry width and height attributes, so CSS is an enhancement rather than load-bearing.
run.sh sourced .env, so every line executed as the application user. A pasted command block landed in that file. .env is parsed as KEY=VALUE. Anything else is named on stderr and ignored.
A stale session made an upload return 401, which was parsed as an empty result list and rendered as nothing at all. The file appeared to vanish. The re-auth sheet, and one wrapper around every write that either succeeds, re-authenticates and retries, or says what went wrong.
google-genai was never in requirements.txt. The real pipeline had never once been capable of running. Pinned, with a test asserting it is declared, and an import error that names the command to fix it.
Inline audio was sent as raw bytes instead of base64, which fails at the transport, so the error would never have mentioned audio. Base64, with every payload shape probed against the SDK's own request normaliser in a test.
SQLite stores UTC. The screen also showed UTC, so a meeting recorded at ten past midnight read 5:11 AM. Stored UTC, rendered in the machine's zone, overridable with ENYGMA_TZ.
A long transcript came back cut off. Asking for one large JSON document meant a single bad character discarded the entire meeting. Constrained JSON decoding, a raised output ceiling, and a salvage parser that keeps every segment that arrived.
A recording is marked transcribing before work starts. A crash in that gap left it there forever, showing a progress bar that could never finish. requeue_stuck() at startup returns them to the queue with a note.
A long transcript was requested as one JSON document, so a response cut off at the end discarded the whole meeting. The model is constrained by a JSON schema, the output ceiling is raised, and a salvage parser keeps every segment that arrived.
The fix for that sent response_mime_type without its required partner and produced a fresh 400, after the audio had already been uploaded. Optional request keys are optional: a rejection about the request's shape falls back to the minimum request. A wrong guess costs one call, not a meeting.
The setup-code field answered every possible mistake — a typo, an expired code, a used code, a PIN — with the same sentence. A four-digit entry is named as a PIN; a wrong length says what the length should be.
